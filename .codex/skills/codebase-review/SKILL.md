# 코드 베이스 검증

작업자의 개발 의도를 기준으로 코드 베이스를 검토하고, 근거가 있는 패턴 이탈과 불필요한 아키텍처를 실제 코드 수정으로 정리한다. AI가 선호하는 추상화나 일반적인 모범 사례로 프로젝트를 재설계하지 않는다.

## 검토 범위

사용자의 요청에서 다음 두 모드 중 하나를 선택하고 시작할 때 범위를 짧게 알린다.

- **1. 전체 코드 베이스**: 프로젝트가 직접 관리하는 소스, 테스트, 실행 설정과 모듈 간 경계를 검토한다. 먼저 파일·모듈 목록을 만들고, 각 영역의 구현과 연결 지점을 읽는다. 의존성 폴더, 빌드 산출물, 자동 생성 파일은 직접 수정 대상에서 제외하되 이를 생성하는 설정은 필요하면 검토한다.
- **2. 현재 변경 사항**: staged·unstaged diff와 신규 파일을 모두 확인한다. 변경 코드뿐 아니라 호출부, 관련 테스트, 같은 책임을 가진 기존 구현을 읽는다. 커밋·브랜치 비교가 요청되면 사용자가 지정한 기준 또는 확인 가능한 merge-base를 사용한다. 기준을 임의로 추측하지 않는다.

모드가 없으면 현재 변경 사항이 있을 때 2번을 선택한다. 변경 사항이 없으면 1번을 선택한다. 사용자가 검토만 요청하면 수정하지 않고 발견 사항을 보고한다. 그 외 이 스킬의 기본 결과물은 검토 후 리팩터링이다.

전체 검토에서 일부 대표 파일만 읽고 전체 검토를 완료했다고 하지 않는다. 저장소가 크면 영역별로 진행하되 검토한 영역과 아직 남은 영역을 명시한다.

## 작업자의 패턴 파악

수정 전에 다음 근거를 읽고 해당 작업에 관련된 패턴을 짧게 정리한다.

1. 사용자의 현재 지시와 이전에 명시한 개발 의도.
2. 적용되는 `AGENTS.md`, 설계·아키텍처 문서, 저장소 규칙.
3. 작업자가 기준으로 지정한 구현과 동일한 역할을 하는 기존 코드.
4. 필요한 범위의 Git 이력과 서로 다른 위치에서 반복되는 구현 관례.

현재의 명시적 지시는 오래된 코드 관례보다 우선한다. 문서와 코드가 충돌하면 어느 쪽을 기준으로 삼을지 근거를 밝힌다. 특정 코드가 작업자의 구현이라는 정보가 없으면 작성자를 단정하지 않는다. Git 작성자나 코드 문체만으로 사람·AI 여부를 판별하지 않는다. 최근 AI가 추가한 코드나 현재 diff를 그대로 기존 개발 패턴의 근거로 삼지 않는다.

관련 근거에서 다음을 확인한다: 책임을 나누는 방식, 파일·폴더 위치, 호출과 데이터 흐름, 명명, 의존성 방향, 추상화 수준, 오류 처리, 입출력 모델, 설정·외부 서비스 연결, 테스트 관례. 모든 항목을 억지로 적용하지 않는다.

패턴이 섞여 있으면 수정 대상과 같은 역할·계층에 있는 구현을 우선 비교한다. 명확한 근거가 없으면 이를 '의도 확인 필요'로 분류하고 추측으로 구조를 바꾸지 않는다. 확인이 필요한 부분을 제외한 검토·수정은 계속한다.

## 이탈 판단

발견 사항마다 **대상 위치 → 기준 패턴과 근거 → 실제 차이 → 동작·유지보수 영향 → 최소 수정**을 연결한다.

특히 다음과 같은 차이를 확인한다.

- 기존 계층을 우회하거나 같은 책임을 다른 위치에 다시 구현한 코드.
- 요청 범위를 넘어 추가한 추상화·설정·의존성·대체 동작.
- 기존 흐름과 다른 데이터 모델, 오류 처리, 인증·설정 또는 외부 요청 방식.
- 실제 사용처 없는 범용화, 불필요한 중간 계층, 중복 로직.
- 작업자가 선택한 아키텍처를 이유 없이 바꾸거나 기존 기능을 미완성 코드·임시 데이터로 대체한 구현.

차이가 있다는 이유만으로 결함이라고 판단하지 않는다. 명시적인 새 요구사항, 프레임워크 제약, 의도된 마이그레이션 때문에 필요한 차이는 유지한다. 자주 반복되는 코드라도 명백한 버그를 패턴이라는 이유로 복제하지 않는다. 취향 차이만 있는 경우는 수정 대상에서 제외한다.

발견 사항을 다음과 같이 구분한다.

- **리팩터링 가능**: 근거가 분명하고 외부 동작을 유지한 채 기존 패턴으로 정리할 수 있다.
- **동작 수정 필요**: 의도와 다른 실행 결과나 회귀가 있다. 사용자의 요청에 포함된 수정은 처리하되 리팩터링과 구분해 설명한다.
- **의도 확인 필요**: 근거가 충돌하거나 공개 인터페이스·데이터 구조·아키텍처의 선택이 필요하다. 필요한 결정만 질문한다.

## 리팩터링

기존 변경 사항을 먼저 확인하고 작업자의 수정 의도를 보존한다. 파일 전체를 과거 버전으로 되돌리거나 다른 변경을 덮어쓰지 않는다.

확인된 이탈만 기존 패턴으로 정리한다. 기존 유틸리티·모델·호출 경로를 재사용하고 필요한 범위에서 책임을 원래 계층으로 옮긴다. 일반적인 '깔끔한 코드'를 이유로 새로운 패턴을 도입하거나 저장소 전체의 포맷을 바꾸지 않는다.

리팩터링은 입출력, 오류 의미, 설정 기본값과 외부 동작을 유지한다. 데이터 삭제, 새 의존성 도입, 대규모 구조 변경, 계약 변경이 필요하면 먼저 필요성을 확인하고 현재 요청의 권한 범위 안에서 진행한다. 단순하고 되돌릴 수 있는 코드 정리에 별도 승인 절차를 만들지 않는다.

## 검증과 보고

수정 전 기존 검증 상태를 확인하고, 수정 후 변경에 맞는 테스트·타입 검사·린트·빌드를 실행한다. 책임 이동과 호출 경로 변경은 실제 소비 지점에서 확인한다. 기존 테스트가 검증하지 않는 중요한 동작만 추가 테스트로 보강한다. 파일명이나 소스 문자열만 검사하는 테스트를 만들지 않는다.

검증 실패가 발생하면 이번 수정으로 인한 실패와 기존 실패를 구분한다. 실패를 숨기거나 테스트를 약화해 통과시키지 않는다. 수행할 수 없었던 검증과 남은 위험을 기록한다.

최종 보고에는 다음을 짧게 담는다.

- 검토 모드와 실제 검토 범위; 전체 검토라면 누락 영역.
- 기준으로 삼은 작업자의 패턴과 구체적인 파일·문서 근거.
- 발견한 이탈과 실제 리팩터링 내용; 동작 수정은 별도로 표시.
- 실행한 검증 결과와 남은 의도 확인 사항.

근거가 있는 이탈이 없다면 이를 그대로 보고하고 수정하지 않는다. 사용자가 요청하지 않은 커밋·푸시·배포는 하지 않는다.
